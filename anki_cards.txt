"What's wrong with this Elixir TCP server code?<br><br><pre>defmodule Commands.Handler do<br>  def handle_connections_async(socket) do<br>    Task.start(fn -> Commands.Echo.handle_connections_async(socket) end)<br>    Task.start(fn -> Commands.Ping.handle_connections_async(socket) end)<br>  end<br>end<br><br># Where Echo and Ping each call :gen_tcp.accept(socket)</pre>"	"<b>Race condition on :gen_tcp.accept/1</b><br><br>Both Tasks call <code>accept</code> on the <b>same listening socket</b> concurrently. Only one process wins each incoming connection.<br><br>If the wrong handler wins (e.g. Ping accepts an ECHO client), it silently drops the connection — no response is sent.<br><br><b>Fix:</b> Use a single accept loop that spawns a Task <b>per client</b>, not per command type. Dispatch to the right handler <i>after</i> parsing the command.<br><br><pre>def accept_loop(socket) do<br>  {:ok, client} = :gen_tcp.accept(socket)<br>  Task.start(fn -> handle_client(client) end)<br>  accept_loop(socket)<br>end</pre><br><br><b>Key principle:</b> Parallelize at the <i>client</i> level (many client handlers), not at the <i>accept</i> level (competing acceptors)."
"What is the underlying data structure of an Elixir list?"	"<b>Singly-linked list</b><br><br>Each node holds a value and a pointer to the next node. There is no pointer backwards.<br><br><pre>[1 | [2 | [3 | []]]]<br><br>1 → 2 → 3 → []<br>↑<br>head (only free access point)</pre><br><br>You always enter from the head. There is no shortcut to the middle or end."
"What's wrong with this code?<br><br><pre>result = Enum.reduce(items, [], fn x, acc -><br>  acc ++ [transform(x)]<br>end)</pre>"	"<b>O(n²) — appending in a loop</b><br><br><code>acc ++ [item]</code> copies the entire accumulator on every iteration. As <code>acc</code> grows, each copy gets more expensive: 1 + 2 + 3 + ... + n = O(n²).<br><br><b>Fix — prepend + reverse once:</b><br><pre>result = Enum.reduce(items, [], fn x, acc -><br>  [transform(x) | acc]<br>end)<br>|&gt; Enum.reverse()</pre><br><br>Prepend is O(1). One final reverse is O(n). Total: O(n) instead of O(n²)."
"What's wrong with this code?<br><br><pre>big_list = Enum.to_list(1..10_000)<br>small_list = [99, 100]<br>result = big_list ++ small_list</pre>"	"<b>O(n) where n = length of left side</b><br><br><code>left ++ right</code> copies every node in <code>left</code> and points the last copied node at <code>right</code>. The right side is shared, not copied.<br><br><b>Fix — put the shorter list on the left when possible:</b><br><pre>small_list ++ big_list  # O(2) — only copies small_list</pre><br><br>If you must append to the end, this cost is unavoidable. Consider whether you can redesign to prepend instead."
"What's wrong with this code?<br><br><pre>list = [1, 2, 3, 4, 5]<br>if length(list) > 0 do<br>  # do work<br>end</pre>"	"<b>length/1 is O(n) — overkill for an emptiness check</b><br><br><code>length/1</code> walks every node to count them. Just to check if the list is non-empty, you traverse the whole thing.<br><br><b>Fix — pattern match or compare:</b><br><pre># Option 1: pattern match<br>case list do<br>  [] -&gt; :empty<br>  [_ | _] -&gt; # do work<br>end<br><br># Option 2: guard<br>if list != [] do<br>  # do work<br>end</pre><br><br><code>length/1</code> is only worth it when you actually need the count."
"What's wrong with this code?<br><br><pre>to_remove = Enum.take(state[key], n)<br>updated = List.delete(state[key], to_remove)</pre>"	"<b>List.delete/2 searches by VALUE, not position</b><br><br><code>List.delete(list, item)</code> walks the list looking for the first element equal to <code>item</code>. Here <code>to_remove</code> is a list, so it's looking for that list <i>as an element</i> inside the outer list — almost certainly not found.<br><br>Even if found, it only removes ONE element.<br><br><b>Fix — use Enum.drop to remove from the head:</b><br><pre>to_remove = Enum.take(state[key], n)<br>updated = Enum.drop(state[key], n)</pre><br><br><code>Enum.drop/2</code> removes the first n elements from the head. O(n), correct, and simple."
"What are the costs of head vs tail operations on Elixir lists?<br><br><pre># Head operations<br>[x | list]<br>hd(list)<br>[_ | rest] = list<br>Enum.take(list, k)<br>Enum.drop(list, k)<br><br># Tail operations<br>list ++ [x]<br>List.last(list)<br>Enum.take(list, -k)<br>Enum.drop(list, -k)</pre>"	"<b>Head = cheap, Tail = expensive</b><br><br><b>Head operations — O(1) or O(k):</b><br>• <code>[x | list]</code> — prepend: O(1)<br>• <code>hd(list)</code> — read head: O(1)<br>• <code>[_ | rest] = list</code> — pop head: O(1)<br>• <code>Enum.take(list, k)</code> — first k: O(k)<br>• <code>Enum.drop(list, k)</code> — skip k: O(k)<br><br><b>Tail operations — all O(n):</b><br>• <code>list ++ [x]</code> — append: O(n), copies entire list<br>• <code>List.last(list)</code> — read last: O(n), walks whole list<br>• <code>Enum.take(list, -k)</code> — last k: O(n), must find length first<br>• <code>Enum.drop(list, -k)</code> — drop last k: O(n)<br><br><b>Rule:</b> Negative indices always mean 'walk the whole thing first.'"
"What's wrong with this code?<br><br><pre>def handle_call({:pop_list_element, key}, _from, state) do<br>  [item | rest] = state[key]<br>  {:reply, item, Map.put(state, key, rest)}<br>end</pre>"	"<b>Crashes on nil or empty list</b><br><br>If <code>state[key]</code> is <code>nil</code> (key doesn't exist) or <code>[]</code> (empty list), the pattern match <code>[item | rest] = ...</code> raises a <code>MatchError</code>.<br><br><b>Fix — add guard clauses:</b><br><pre>def handle_call({:pop_list_element, key}, _from, state) do<br>  case Map.get(state, key) do<br>    nil -&gt; {:reply, nil, state}<br>    [] -&gt; {:reply, nil, state}<br>    [item | rest] -&gt; {:reply, item, Map.put(state, key, rest)}<br>  end<br>end</pre><br><br>The <code>[h | t]</code> pattern match itself is O(1) — perfect for head removal. Just protect against nil/empty."
"When should you use :queue instead of a list in Elixir?"	"<b>When you need efficient operations on BOTH ends</b><br><br>Lists are singly-linked: head ops are O(1), tail ops are O(n).<br><br><code>:queue</code> uses two internal lists (front + back) to give amortized O(1) on both ends:<br><pre>q = :queue.new()<br>q = :queue.in(1, q)        # add to back  — O(1) amortized<br>q = :queue.in_r(2, q)      # add to front — O(1) amortized<br>{{:value, v}, q} = :queue.out(q)   # pop front — O(1) amortized<br>{{:value, v}, q} = :queue.out_r(q) # pop back  — O(1) amortized</pre><br><br><b>Use :queue when:</b><br>• You need both LPUSH and RPUSH (like Redis lists)<br>• You're building a FIFO queue<br>• You append to one end and consume from the other"
"What's wrong with this code?<br><br><pre># RPUSH implementation<br>RedisCache.update(cache_pid, %{key =&gt; values})<br>updated_list = RedisCache.get(cache_pid, key)<br>length = length(updated_list)<br>:gen_tcp.send(client, &quot;:#{length}\r\n&quot;)</pre>"	"<b>3 GenServer calls + O(n) length for one operation</b><br><br>Each <code>GenServer.call</code> is a message send + receive round-trip. Here you do: get (check exists) → update (append) → get (read back) → length (walk list). That's excessive serialization and multiple list traversals.<br><br><b>Fix — return the new length directly from the update call:</b><br><pre># In GenServer:<br>def handle_call({:update, kv}, _from, state) do<br>  [{key, value}] = Map.to_list(kv)<br>  new_list = Map.get(state, key, []) ++ value<br>  new_state = Map.put(state, key, new_list)<br>  {:reply, length(new_list), new_state}<br>end<br><br># In caller — one call instead of three:<br>new_length = RedisCache.update(cache_pid, %{key =&gt; values})<br>:gen_tcp.send(client, &quot;:#{new_length}\r\n&quot;)</pre>"
"What data structure should you pick?<br><br>• Need random access by index<br>• Need fast append AND prepend<br>• Need key-value lookup<br>• Need frequent length checks"	"<b>Pick the right tool:</b><br><br>• <b>Random access by index</b> → <b>Tuple</b><br><code>elem(tuple, i)</code> is O(1). Lists are O(n) for index access.<br><br>• <b>Fast append AND prepend</b> → <b>:queue</b><br>Amortized O(1) on both ends. Lists are O(1) prepend but O(n) append.<br><br>• <b>Key-value lookup</b> → <b>Map</b><br>O(log n) lookup. Lists require O(n) linear scan.<br><br>• <b>Frequent length checks</b> → <b>Store length separately</b><br><code>length/1</code> is O(n) on lists. Track it in a variable/tuple: <code>{list, count}</code>."
"Why does <code>left ++ right</code> copy the left side but not the right?"	"<b>Immutability</b><br><br>The original <code>left</code> list still needs to end at <code>[]</code>. You can't mutate its last node's pointer to point at <code>right</code> instead. So the VM builds a <b>new chain</b> that's a copy of <code>left</code>, with the last node pointing at <code>right</code>.<br><br><code>right</code> is unchanged — the new chain just references it. This is called <b>structural sharing</b>.<br><br><pre>a = [1, 2, 3]    # 1 → 2 → 3 → []<br>b = [4, 5]        # 4 → 5 → []<br>a ++ b            # 1' → 2' → 3' → [4 → 5 → []]<br>                  # copies ↑↑↑    shares ↑↑↑</pre>"
